## What the docs already say (the trail, all verified)

- **SPEC §6** (record types): "Expected receipt (income)" — positive sign, **not** spending,
  "Generated by income schedules (§11)". Income has no category and no target.
- **SPEC §11.1 / §11.3**: an income schedule is kind *expected receipt* (the worked example: Sam's
  salary, fixed amount, monthly, due into the Salary account on the configured payday). It enters
  `projected_low` as a receipt, auto-converts to an actual receipt record at local midnight on the
  due date (§11.2, one instance one state), and its due date *is* the planning cycle's payday.
- **SPEC §15.3** (v0.3.0, All Transactions code table): the `BAC` row for `receipts` (income) is
  "**reserved, not rendered in v1**". "Income is deferred with income itself: §11.3 records income
  only by schedule conversion, so a one-off third-party credit is recorded as other money in
  (counterparty plus mandatory note) and therefore appears as `TX<`."
- **Plan scope item 8** (agreed 2026-09-20): "Income: **fixed expected receipts in scope** (salary,
  known date, roughly fixed amount) feeding the projection." — i.e. *scheduled* income was always in
  scope; the gap is everything else.
- **Plan decision 55** (Phase 3, resolves OQ5): dedicated `receipts` table, NOT a reuse of
  `purchases`/`allocations` — income carries no category or target, so forcing it through the
  exact-total split machinery would be a lie. The estimate engine reads receipts as +signed pence.
- **Plan decision 103** (household choice, 2026-09-23): **income rows deferred; `BAC` reserved.**
  The sketch's `BAC` row ("Acme windows · Income: Janet") was not producible: `receipts` had no
  source-name column, no manual entry existed, and no page listed income. "Rendering that row would
  need schema, an entry form and a list — an income feature, not a display tweak, and one that
  reopens the income-analysis question §12/§16 deliberately excludes. **Scheduled income will slot
  in later as `BAC`**; meanwhile a one-off third-party credit is recorded as other money in."
- **Plan decision 105**: a full transfers/**income** history was considered and rejected *at that
  time* as a second feature area (the v0.3.0 deep-link work stayed display-only).
- **Plan OQ2** (still open): a "shift to previous working day if weekend/bank holiday" toggle for
  income schedules only (salaries commonly pay on the last working day).
- **SPEC §16 / insights-view**: insights see no income at all ("no phantom income, no phantom
  spending"); borrowed money is never income (SPEC §10.2). Income *analysis* (income-vs-spending,
  category breakdown of receipts) is deliberately out of scope.

## Code state, verified this session (main @ `7ccc0eb`)

**The data layer already exists and is complete.**

- `src/lib/db/schema.ts:386` — `receipts`: `id`, `schedule_instance_id` (null for manual entries),
  `pot_id`, `amount_pence` (CHECK > 0), `occurred_at` + `occurred_date` (shared backdating rules),
  `entered_by`, `note` (280 chars), `voided_at/by/reason`, `version`. Indexes on
  `(pot_id, occurred_at)`, `occurred_date`, `schedule_instance_id`. **No source/counterparty
  column; no category column (by design).**
- `src/lib/records/receipts.ts` — a full module: `createReceipt` (transactional, audited
  `receipt.create`, pot-exists + positive-pence checks, `resolveOccurred` backdating),
  `editReceipt` (version-guarded; pot/amount/date/note), `voidReceipt` (reason, audited),
  `getReceipt`, and `listReceipts` (filters `potId`/`dateFrom`/`dateTo`/`includeVoided`/`limit`,
  default 200, capped 1000, ordered `occurred_at desc, id desc`).
- `src/lib/records/schedules.ts:679` — conversion writes receipts via `createReceipt` with
  `note: From schedule "…"`, back-referenced both ways; idempotent (crash repair via
  `markConverted`).
- `src/lib/records/estimates.ts:13` — the estimate already includes `+ Σ receipts into P after t`,
  under §7.1's sign-aware same-day rule (a date-only receipt is a *credit*: absorbed when it shares
  the checkpoint's local date).
- `src/lib/records/projection.ts` — expected receipts apply on their due day; within a day,
  outgoings apply before receipts (conservative).
- `src/lib/backup` — archive format 2 snapshots the whole database file, so receipts are persisted;
  **new columns/tables do not bump the format** (precedent: migration `0005_external_money.sql`
  added `debts` + `external_movements`; v0.2.0 notes: "No backup-format change … the new tables ride
  along in the next backup automatically").

**The UI layer is absent — that is the entire gap.**

- No `addReceipt`/`editReceipt`/`voidReceipt` action in `src/app/actions.ts` (28 actions exist;

- Scheduled income *is* visible today, but only as schedule data: /recurring list ("income" label,

- SPEC §15.2's page table has no Income page; "Accounts & Pots" is where boundary money
  (borrow/repay/swap/other) is entered and listed — the closest home for income.

## The gap, precisely

Income can enter the app today in exactly one way: a `kind='receipt'` schedule converts at local
midnight. There is **no way to record a one-off income** (a deposit, a refund from a third party,
a gift, freelance work, a bonus) and **no way to see any receipt record** — it moves the estimate
and the projection but appears in no list. The documented interim is "other money in" (`TX<`) with
counterparty + mandatory note, which the household sketch's `BAC` row shows they want proper
income rows instead.

## Proposed design (defaults to confirm with the household before building)

Scope: make income **visible and manually recordable**, without touching the estimate/projection
engine (already correct) and without reopening income analysis (decision 103).

**Phase A — manual income entry (the real gap)**

1. **Schema:** additive migration `0006_income_source.sql` — optional `source` column (text,
   nullable, ~80 chars) on `receipts` = who/what it came from ("Acme windows"). Converted receipts
   keep `source` null and show the schedule name (already resolvable via the back-reference).
   Precedent: `0005`. No backup-format change.
   - *Household decision:* is `source` (free text) enough, or does one-off income also need
     person attribution? The sketch's "Income: Janet" is ambiguous (Janet paid us? income for
     Janet?). **Default: `source` only** — income has no category/target by design, and the
     household can always express more in the note (280 chars).
2. **Actions:** `addReceiptAction`, `editReceiptAction`, `voidReceiptAction` in
   `src/app/actions.ts`, mirroring `addExternalMovementAction` (parsing, auth, actor, money input,
   error mapping). The domain functions already exist and are tested.
3. **Entry form:** a small `IncomeForm` (amount, pot, date, optional source, optional note)
   offered in **Quick Entry** (mobile, alongside the loan/other movement forms) and on the
   **Accounts & Pots** page (desktop, beside the boundary-money entry).

**Phase B — income list (visibility)**

4. Host it in **Accounts & Pots**, per selected pot like the boundary-money list: recent receipts
   for that pot with `source`, note, a quiet "From schedule" marker for converted ones, and inline
   edit/void (the canonical form, per the §15.3 rule that lists link to canonical records).
   Stable row anchors `receipt-{id}` + `?receipt={id}` force-render, exactly the decision-105
   pattern. Built on the existing, currently-unused `listReceipts`.
   - *Household decision:* /pots vs a dedicated Income page in the nav. **Default: /pots** — no nav
     growth, and boundary money already lives there.

**Phase C — `BAC` rows in All Transactions (closes the v0.3.0 deferral)**

5. `activity.ts`: render receipts as rows — code `'BAC'` (add to the `ActivityCode` union), family
   `'receipt'`, source = `source` ?? schedule name (converted) ?? "Income", category `—` (income
   has none), direction always `in` (a receipt is a credit to its pot), note as stored, link to the
   Phase B canonical row; converted receipts additionally get the secondary `/recurring#schedule-{id}`
   link the DD/SO rows have.
   - Docs: unreserve `BAC` in SPEC §15.3's code table; record new numbered decisions (109+) in
     `IMPLEMENTATION_PLAN.md` as agreed with the household; replace this handoff.

**Optional, separate decision — OQ2:** the working-day-shift toggle for income schedules
(salaries paying on the last working day). It changes instance generation in `schedules.ts` and is
independent of Phases A–C. **Default: do not bundle** unless the household asks.

## Watch out for

- **Do not touch estimates, projection or insights** — they are already correct (receipts as
  +signed pence; insights deliberately blind to income), and existing tests pin that.
- Date-only receipts share §7.1's sign-aware rule (a same-day credit is *absorbed*): the form must
  use the same `resolveOccurred` semantics as every other record — no invented timestamps.
- Schedules are never deleted and kind is fixed at creation, so a converted receipt's origin is
  always resolvable; show the schedule name in the Source cell, not the `From schedule "…"` note.
- A pot with *any* record — including receipts — cannot be archived (SPEC §4), so an archived pot's
  income list is empty by construction; the target selector already lists archived pots via
  `listPotsIncludingArchived` for history.
- `listReceipts` is capped at 1000; if Phase C reuses per-family fetches, apply the activity
  row-cap pattern (500 rows + hidden count from `count(*)`, not from what was fetched).
- Income **analysis** stays out (decision 103, §12/§16): no income-vs-spending charts, no
  categories for income. Rows + list + entry are visibility and record-keeping, not analysis.
